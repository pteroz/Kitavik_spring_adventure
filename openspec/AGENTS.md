# Правила работы агента со спеками (OpenSpec)

Проект использует OpenSpec-структуру: спеки — источник правды о поведении, код — источник правды о реализации. Спека описывает **что** система делает; файлы и классы — в `../project.md`.

## Каталоги

- `../project.md` — контекст проекта, стек (текущий Python/Arcade и целевой Godot), жёсткие ограничения, конвенции
- `../specs/<capability>/spec.md` — живые спеки возможностей (текущее поведение игры)
- `../changes/<id>/` — предложения изменений и их дельты спек; завершённые — в `../changes/archive/`

CLI `openspec` не установлен (осознанно, чтобы не тянуть сеть) — валидация и архивация делаются вручную по правилам ниже.

## Когда нужен proposal, а когда нет

- **Нужно** (`openspec/changes/<id>/`): новая возможность, изменение видимого поведения, изменение схемы данных/формата уровня, затрагивающее пользователя.
- **Не нужно**: багфикс к спеке, рефакторинг без изменения поведения, правки ассетов/верстки, инфраструктура сборки.
- Сомневаешься — спроси пользователя.

## Жизненный цикл изменения

1. **Proposal.** Создай `changes/<id>/` (id — kebab-case по сути, например `add-double-jump`). Внутри:
   - `proposal.md` — `## Why` (зачем), `## What Changes` (что меняется, по возможностям), `## Impact` (какие спеки/файлы затрагивает)
   - `tasks.md` — `## 1. Implementation` и `## 2. Validation` с чекбоксами; Validation обязана включать пункт про реальный запуск игры (см. ниже)
   - `design.md` — опционально: технические решения и альтернативы
   - `spec/<capability>/spec.md` — дельта: секции `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements` с полными блоками `### Requirement:` (модифицируемое требование переписывается целиком, помечай `(modified)` в заголовке)
2. **Согласование с пользователем** — proposal и план реализации до написания кода.
3. **Имплементация** — строго по tasks.md, отмечая чекбоксы. Сверяйся с ограничениями из `project.md`.
4. **Архивация.** После подтверждения пользователем, что всё работает: перенеси дельты в живую спеку (`ADDED` — добавить блок, `MODIFIED` — заменить блок, `REMOVED` — удалить), папку изменения перенеси в `changes/archive/`.

## Формат требований

```markdown
### Requirement: Короткое имя поведения
Система должна <проверяемое утверждение>.

#### Scenario: Название сценария
- **WHEN** <условие>
- **THEN** <результат>
- **AND** <дополнительный результат>
```

- Тексты требований и сценариев — на русском (как весь проект); ключевые слова структуры — английские (`Requirement`, `Scenario`, `WHEN/THEN`).
- Каждый `Requirement` — минимум один `Scenario`.
- Требование формулируется через наблюдаемое поведение, без упоминания классов и файлов.

## Валидация (специфика проекта)

- Игра desktop-ориентированная. Базовая проверка — **headless-прогон** движка без окна (парсинг сцен/скриптов, отсутствие ошибок рантайма), затем **реальный запуск окна** и ручная проверка поведения.
- Окно игры открывается на экране пользователя — **не запускать видимый прогон без спроса** (агент спрашивает, пользователь разрешает).
- Числовые константы «ощущения» (скорости, импульсы, таймеры) сверять с living-спеками и `project.md`; расхождение спека ↔ код не прятать, а сообщать и исправлять.

## Правило актуальности

Спека не должна расходиться с кодом. Если при работе обнаружено расхождение «спека ≠ код» — не молчи: сообщи пользователю и исправь спеку (или код) как часть задачи. Для мигрируемого проекта это особенно важно: living-спеки описывают поведение, которое Godot-порт обязан воспроизвести.
